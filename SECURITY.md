# Модель безопасности PersonGuard

## Формат PGD3 и ключи входа

PGD3 добавляет к структуре PGD2 префикс: `PGD3`, 32-битную длину JSON (big-endian, не более 8192 байт), затем JSON с `CredentialId` (1–1024 байта), `Salt` (32 байта), `Nonce` (12 байт) и `WrappedKey` (48 байт). Бинарные значения сериализуются в base64. За префиксом следует структура PGD2. Весь префикс и преамбула PGD2 используются как AAD при шифровании содержимого AES-256-GCM; подмена метаданных и удаление префикса обнаруживаются. Внешние поля проверяются до обращения к WebAuthn и до запуска KDF. Имя сейфа и имена записей в метаданные passkey не попадают.

Ключ данных оборачивается вторым независимым ключом: HKDF-SHA-256 от 32-байтного результата WebAuthn PRF, соли и контекста `PersonGuard PGD3 passkey wrap v1`. Для обёртки используется AES-256-GCM с новым nonce и CredentialId как AAD. PRF получает одну и ту же случайную соль для данного credential; Windows преобразует её по стандарту PRF. Результат PRF, ключ обёртки и открытый ключ данных не записываются на диск и очищаются в `finally`. Сам passkey остаётся у системного провайдера. Исходный Argon2id-конверт сохраняется для резервного открытия мастер-паролем.

Нативный Windows WebAuthn API используется с обязательной проверкой пользователя (UV) и свежим challenge. Проверяются RP hash, UP/UV, credential ID и наличие 32-байтного PRF-выхода. Доступ к данным доказывается успешной аутентифицированной расшифровкой ключа и содержимого; серверной сессии и проверки аккаунта здесь нет. Регистрация требует мастер-пароль и одну успешную PRF-проверку после создания ключа. Нет обхода через простой успешный ответ WebAuthn или сохранённый в открытом виде ключ. При блокировке Windows результат незавершённой операции отбрасывается.

RP ID `personguard.local` фиксирован; это локальное пространство имён приложения. Его изменение потребует повторной регистрации ключей. Нативная интеграция и PRF через транспорт iPhone/iCloud требуют ручной проверки на целевых устройствах. WebAuthn API ниже версии 6 и провайдеры без PRF не поддерживаются. FIDO-соединение с телефоном может использовать сетевую инфраструктуру провайдера и Bluetooth; локальное открытие мастер-паролем от них не зависит.

Отключение passkey и смена мастер-пароля создают новый случайный ключ данных: старый слот passkey, прежний мастер-пароль и однажды похищенный ключ не открывают ни текущее, ни последующие сохранения. Старые копии файла остаются доступны прежним способом. Смена мастер-пароля отключает passkey — его нужно подключить заново. Удаление passkey у провайдера не уничтожает мастер-парольный способ открытия. Синхронизация ключа через iCloud добавляет доверие к защите устройств и учётной записи провайдера, но не передаёт ему содержимое `.pgd`.

## Формат PGD2

`.pgd` — бинарный контейнер. Открытым остаётся только минимальный заголовок с версией, идентификаторами алгоритмов, параметрами Argon2id, солью и nonce. Название сейфа, сайты, URL, username/email, телефоны, пароли, избранное и даты находятся внутри аутентифицированного шифротекста.

1. Для каждого сейфа создаётся случайный 256-битный ключ данных.
2. Из мастер-пароля и случайной 128-битной соли Argon2id выводит ключ шифрования ключа: 128 MiB памяти, 4 прохода, параллелизм 2.
3. Ключ данных оборачивается AES-256-GCM с отдельным 96-битным nonce.
4. Содержимое сейфа шифруется тем же стандартом с новым случайным nonce при каждом сохранении.
5. Заголовок и обёрнутый ключ передаются как дополнительные аутентифицируемые данные. Любое изменение параметров, ключа, метаданных или содержимого приводит к отказу открытия.
6. При смене мастер-пароля генерируются новая соль и nonce и переоборачивается только случайный ключ данных. Сам мастер-пароль нигде не сохраняется.

Запись выполняется через временный **уже зашифрованный** файл с принудительной записью на диск и последующей заменой целевого файла. Размер импортируемого контейнера и параметры KDF ограничены до выделения ресурсов.

## Защита открытого приложения

- Ключ данных и пароли записей хранятся в памяти зашифрованными `CryptProtectMemory(SAME_PROCESS)`: ключ находится в ядре и привязан к процессу, поэтому снятый другим процессом дамп памяти не расшифровывается. Открытый массив байтов создаётся только на время шифрования, показа или копирования и затем обнуляется.
- При запуске DACL процесса ограничивается: другим процессам пользователя доступны только запрос базовых сведений, ожидание и завершение. Чтение и запись памяти, создание потоков и дублирование дескрипторов запрещены; ACE `OWNER RIGHTS` не даёт владельцу вернуть себе `WRITE_DAC`. Обойти это может только код с `SeDebugPrivilege`, то есть администратор: работайте под стандартной учётной записью.
- Поля мастер-пароля и пароля приложения используют `SecureString`; временные UTF-8 буферы обнуляются.
- Локальный пароль приложения проверяется через Argon2id. Его соль, хеш и настройки хранятся в отдельном DPAPI-контейнере текущего пользователя Windows.
- Windows Hello можно включить только после настройки резервного пароля приложения. Оно используется при входе и для чувствительных действий. Смена мастер-пароля всегда требует текущий мастер-пароль: PIN Windows Hello для этого недостаточен.
- Защита окна, разрешение копирования, блокировка при потере фокуса и автоблокировка дублируются внутри зашифрованного сейфа. Локальный `security.pgcfg` доступен для записи любому процессу пользователя, поэтому при открытии сейфа применяется самый строгий из двух наборов. Пароль приложения и Windows Hello на стартовом экране — это барьер интерфейса, а не криптографическая защита: сейф всегда требует мастер-пароль или passkey.
- Показ и копирование пароля требуют подтверждения Windows Hello, ключом входа или мастер-паролем. Подтверждение и открытие сейфа действуют 5 минут (настраивается: каждый раз, 1, 5 или 15 минут; значение хранится и в сейфе). Любая блокировка сейфа или Windows сразу сбрасывает это окно. Смена мастер-пароля и управление ключом входа всегда требуют мастер-пароль. Логин и телефон видны на карточке и копируются без подтверждения. Показ пароля закрывается через 7 секунд.
- Копирование выключено по умолчанию. После явного включения запись помечается для Windows как исключённая из истории, облачной синхронизации и обработки мониторами буфера, а затем очищается через 20 секунд, если содержимое не было заменено другой программой.
- При блокировке сейф, защищённые секреты, граф и ссылки интерфейса очищаются; запускается принудительная очистка управляемой памяти.
- Загрузка DLL ограничена системными и явно разрешёнными каталогами; исполняемые образы из сети и low-integrity областей блокируются, а устаревшие точки внедрения отключаются. Приложение работает без прав администратора и допускает только один экземпляр.

## Граница защиты

PersonGuard надёжно защищает закрытый файл и обнаруживает его подмену, но ни одно desktop-приложение не может гарантированно победить вредоносный код, уже работающий с правами пользователя, администратора или ядра. Такое ПО способно перехватывать клавиатуру, читать память процесса, подменять исполняемый файл или фотографировать экран внешней камерой.

Если `PersonGuard.exe` лежит в папке, куда можно писать без прав администратора (Загрузки, `%LOCALAPPDATA%`, папка проекта), вредоносная программа пользователя может подменить exe и перехватить мастер-пароль. Приложение предупреждает об этом в разделе «Безопасность». Храните exe в `C:\Program Files\PersonGuard`.

Любой процесс пользователя может запросить у Windows проверку passkey для `personguard.local`: идентификатор ключа и соль хранятся в заголовке файла открыто, а Windows не привязывает этот RP ID к PersonGuard. Подтверждайте окно Windows Hello или телефона, только если сами только что запросили открытие сейфа. Значения, показанные в окне, доступны программам через UI Automation так же, как экранным дикторам.

Защита окна уменьшает риск обычных снимков/трансляции экрана, но не является DRM и зависит от Windows. `SecureString`, DPAPI, короткое время показа и обнуление буферов сокращают поверхность атаки, но не делают секрет невидимым для отладчика или скомпрометированной ОС.

Рекомендуется:

- обновлять Windows и антивирус, включить Secure Boot, BitLocker и защиту от изменений Microsoft Defender;
- использовать стандартную учётную запись без постоянных прав администратора;
- задавать уникальный мастер-пароль длиной не менее 14 символов;
- держать приложение заблокированным, когда оно не используется;
- не включать буфер обмена без необходимости и отключить историю/облачную синхронизацию буфера Windows;
- хранить резервную копию `.pgd` отдельно и периодически проверять её открытие;
- использовать только сборки с ожидаемым SHA-256 и, для распространения, с доверенной Authenticode-подписью.

## Подпись релиза

Текущая локальная сборка помечается в интерфейсе как `DEV-сборка без подписи`, если сертификат отсутствует. Нельзя честно создать доверенную издательскую подпись без закрытого ключа владельца сертификата.

Скрипт `build-desktop.ps1` поддерживает реальную подпись: укажите отпечаток сертификата подписи кода из хранилища текущего пользователя в переменной `PERSONGUARD_SIGNING_THUMBPRINT`. Сборка завершится ошибкой, если подпись не получила статус `Valid`.
